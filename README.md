# cyberduck.club — the Robot Brawl site

Static site, published to GitHub Pages by `publish_site.zsh`. No build step:
what is in this folder is what is served.

## The two data files refresh on completely different clocks

`champions/` renders real champions in 3D out of two files in `data/`, and the
single most important thing to know about them is that **only one of them
refreshes on its own.**

| file | what it holds | regenerated by | needs Unity | cadence |
|---|---|---|---|---|
| `data/showcase.json` | who is champion of each class, their build, and the clip of the fight that won it | `tools/bake_showcase.py` against the live ladder API | no | daily, or any time you run it |
| `data/parts.json` | the game's part catalogue: sizes, materials, and the **visual recipe** for every part | `RobotBrawl.Editor.ExportPartTable.Export()` in the Unity editor | **yes, and in PLAY MODE** | only when the game's parts change |

### Why `parts.json` is not a hand-written table

The page rebuilds each robot from the same build text the game uses. A
hand-copied size table would be a second source of truth that drifts silently —
the model on the site would slowly stop being the robot in the game, and nothing
would fail. So the exporter reads `P1PartDef.Palette()` and `MatDB` directly.

It goes further than sizes. **A part in this game is not a box**:
`PartVisualFactory.BuildPart` assembles each one from a body, end caps, rows of
bolt cylinders, hazard ribs, socket dots and glowing accents — 398 primitives
across the catalogue, 33 for a single beam. The site drew one flat box per part
until 2026-08-18, which is why the machines read as toy blocks here and as
machinery in the game.

Rather than reimplement those recipes in JavaScript, the exporter **runs
`BuildPart` and records what it produced**. It builds each part twice under two
different fallback colours so it can *measure* which sub-pieces follow the
player's chosen alloy and which are fixed accents, instead of guessing. Whatever
the game draws is what the site draws.

### `parts.json` now has TWO consumers

`how-to-play/` renders the whole catalogue from it — the part shelf, the 3D
inspector and the materials table are all read out of that one file, so a
missing or stale export shows up as a *tutorial teaching the wrong catalogue*
as well as a champions page drawing the wrong machine. The tutorial's renderer
is deliberately a smaller one than the champions page's (one part at a time, no
bloom, no post-processing, no shadow maps): it is the page a brand-new player
opens on a phone, and it should come up fast. Both use the same Unity→three.js
conventions, and if you change one you almost certainly meant to change both:
Z mirrors, euler order is ZXY, and Unity's Cylinder is diameter 1 and HEIGHT 2.

The rest of the tutorial — the four build rules, the leagues, the weight caps,
the sensors and what each one unlocks — is **transcribed** from the game's own
tables rather than read at runtime. It is accurate as of 2026-08-18 and it is
the part of that page that can silently go stale. If you change
`RobotCategory.LADDER`, `Career.Leagues`, `BuilderManager.Validate()`,
`RobotProgram.SensorIdOf()` or `GUSSET_SEAM_MULT`, the tutorial is wrong until
someone edits it.

### ⚠ If you add or restyle a part in the game, re-run the exporter

Nothing will break if you forget, and that is the trap. An unknown part id falls
back to a small plain cube and a known part with no recipe falls back to a plain
box — the page keeps working and quietly shows the wrong machine. There is no
check that can catch this from the website side, because the website has no way
to know what the game looks like.

To re-run it: open the project in Unity, **enter play mode**, and call
`RobotBrawl.Editor.ExportPartTable.Export()`. Play mode is required because the
factory's `Deco()` calls `Object.Destroy`, which is illegal from edit mode.
It writes `website/data/parts.json`. Commit the result.

## Checking the champions page after a change

The page exposes `window.__stage` as a test seam: `mode()`, `model()`, `span()`,
`boxes()`, `cost()`, `seek(t)`, `run(n)`, `settle(n)`, `spin(angle)`,
`isolate()`. `span()` returns the machine's silhouette as a fraction of the
stage, so 1.0 means it exactly fills it and anything above 1.0 is being cut off.
`cost()` returns `{meshes, tris}` for the whole scene.

Watch `cost()` after any change to how parts are built. The recipes would be
1529 draw calls for the FEATHER fight if each sub-primitive were its own mesh;
the pieces of one part are baked into one geometry per material instead, which
brings it to 245. That is invisible on a desktop and is the number most likely
to go wrong on a phone.

Two traps that have each produced a confident wrong answer:

- **A headless/automated browser tab is HIDDEN, and Chrome suspends
  `requestAnimationFrame` in hidden tabs entirely** — measured, 0 frames in
  1200 ms. Animation looks frozen and is fine. Drive the clock with `seek()` /
  `run()` / `settle()`, and take a screenshot to force a paint *before* reading
  any derived value.
- **`resize_window` is a no-op here, but an IFRAME is not.** Mobile layout can
  be reproduced by loading the page in a 390x844 iframe from a scratch local
  page — that is how phone-width layout was first observed in this project. It
  reproduces LAYOUT faithfully; it does NOT reproduce the browser ENGINE, so it
  cannot see a WebKit-only failure (the champions stage booting on Blink at
  390px and dying on iOS Safari is exactly that case).
- **Measure over the whole turntable rotation, not at one angle.** The framing
  is solved per angle. A single sample said the machines fit; sweeping 36 angles
  showed LIGHT was being cut through nearly half its rotation.

## Class chips

The five weight classes are FEATHER, LIGHT, MIDDLE, HEAVY, SUPER. MIDDLE
deliberately renders a "NOBODY OWNS MIDDLEWEIGHT" recruitment card rather than a
machine whenever its champion is a house robot — that is intended, not a
missing model.
